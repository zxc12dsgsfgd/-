# 系统总体设计（初版）

日期：2026-11-20。状态：方案草案，供审阅和详细设计；尚无应用代码、数据库、环境或运行验证。范围与验收依据见 `../01-需求分析/`。

## 1. 方案选择

| 方案 | 优点 | 代价及适用性 |
| --- | --- | --- |
| 前后端分离的模块化单体：React 前端、FastAPI 后端、MySQL、单独后台执行进程 | 模块边界清楚；本地依赖较少；符合既有技术方向 | 需要显式处理任务持久化和单进程调度；推荐首版 |
| 前后端分离并使用独立消息队列与多服务 | 扩容和任务隔离更灵活 | 配置、部署与运维成本较高；首版本地演示尚无证据需要 |
| 服务端模板的单体 | 初始组件较少 | 与已有 React 方向和图谱、PDF 交互需求不一致；改动成本较高 |

推荐模块化单体，按业务模块分层，后台执行进程复用同一后端代码和 MySQL；服务端承担认证、权限和业务规则，不依赖前端隐藏按钮。用户已明确 MySQL、uv 与 Python 虚拟环境；其余技术和具体版本均为拟定选择，需在详细设计及环境验证时落实。

## 2. 数据流与边界

浏览器通过 API 访问后端；后端通过事务操作 MySQL、通过受控文件服务读取本地 PDF。用户选择材料并确认发送范围后，后端向用户配置的外部 AI 服务发起请求，生成的草稿与来源关系保存在本地；未配置或服务失败明确反馈，其他核心功能不依赖该服务。分享访问使用独立公开入口，服务端每次检查令牌、期限、撤销状态及资源范围。具体架构见《系统架构设计》。

## 3. 关键流程

1. 登录后，后端解析身份并对私有资源执行归属校验；列表、详情及文件访问同样受保护。
2. 文献导入先规范化并检查 DOI，缺 DOI 时按标题等提示疑似重复；用户决策后保存。PDF 由后端校验并记录受控存储键，文献与卡片可相互追溯。
3. 文献及卡片变更与可处理事件在同一数据库事务中持久化。后台进程按事件驱动或定时扫描规则；使用唯一执行键与事务保护副作用，并设置规则链深度或其他终止机制，避免循环。故障恢复及并发细节留待详细设计与实测。
4. 用户选材后查看发送范围并主动触发 AI；结果保留来源且为草稿。建议只有确认后才能变更用户数据；导出基于已有材料与真实关联文献。
5. 分享仅暴露用户选择的内容；到期或撤销后无法访问，批注仅在允许时提交。快照与动态引用的具体模型及删除策略待详细设计。

## 4. 安全、质量和部署

采用成熟密码哈希；密钥经服务端加密后保存，加密主密钥由环境变量提供；认证、分享与 AI 接口限流；文件上传限制类型、大小、路径并安全显示用户内容。CORS 使用明确允许来源。具体认证方式、密钥轮换、限流阈值、文件删除与备份方案待详细设计。

本地拟采用项目内的代码、uv 虚拟环境和受控文件目录，MySQL 可通过 Docker Compose 提供；后端 API、后台进程和前端开发服务器各自启动。MySQL 持久化目录和生成文件位置须落实为工作目录内，容器镜像或外部工具自身缓存的位置需在实际搭建时核查，不能在本阶段声称已满足。数据库结构由 Alembic 迁移管理。故障、安全、双用户隔离和核心流程需实际测试；尚未执行任何部署、迁移或测试。
