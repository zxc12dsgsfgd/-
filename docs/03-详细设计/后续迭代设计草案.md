# 后续迭代设计草案

状态：供审阅的方案，尚未实现；接口、数据约束和迁移需逐项细化并验证。数据库不因本文改变。

## 项目空间（FR-028）

建议创建研究项目表及文献、卡片、计划、草稿各自的关联表；每个关联对唯一，外键指向真实资源，写入时同时查询项目和资源的会话所有者。项目状态为进行中、已完成、已归档；归档不删除关联。详情统计来自已授权关联的数据库查询，计划进度沿用现有口径。项目删除须展示“仅删除项目及关联”，单个事务清理关系；被关联对象不得删除。原有文献/卡片独立接口保持可用，列表/详情和删除操作应验证双用户隔离。明确项目资源的最终删除策略与 FR-031 整合后再落库。

## 证据与来源（FR-029）

建议以明确的内容类别和核查状态表示用户意图，保留来源快照、位置和所有者可访问性；来源新增、修改和移除生成可审计变更记录。现有草稿 sources 为快照，不能据此断言源仍存在或具有句子级引用；需要增加可追踪的来源身份和失效状态，同时迁移旧快照时标为来源状态未知，而非自动核实。历史版本及分享快照的行为需分别设计。

实施中的卡片切片：正文类别为未分类、用户解释、AI 建议或用户结论，原文保留在单独的摘录字段；核查状态仅由用户设置，迁移旧卡片为未分类和待核查。卡片版本记录包含新字段。来源关联被解除时保留标题快照并显示已解除；源文献删除时标记不可用。原始草稿选材快照不因修改当前关联而被覆盖，该部分另行实现。

## 备份与回收（FR-030、031）

备份导入建议初版以版本化清单、用户可预览及显式重复策略为基础；附件是否纳入、导入上限和与研究项目/回收站的范围须在实施前确定。避免恢复会话、密码与 AI 密钥；按用户建立独立 ID 映射并校验引用。导入数据库操作尽量单事务，涉及附件需隔离暂存和失败清理并验证。回收站需完整规定所有查询排除软删除对象、恢复时关系冲突处理、分享快照及附件读权限、永久删除和清理失败；不假设自动清理已实现。

## 阅读模板与批量（FR-032、033）

建议结构化字段与自由笔记并存；字段转卡片保留文献和内容的用户填写性质，原文仅在用户明确选择并提供时记录。批量接口限制项目数，逐项授权；采用全拒绝或逐项结果应在具体接口固定并在 UI 中准确展示，不能默默跳过；状态变化须走现有业务和工作流逻辑。

## 与现有实现的差异和影响

- 现有文献删除会断开卡片来源并保留快照，卡片删除会删除版本/关系；回收站要求先可恢复，不能仅沿用物理删除。改动会影响图谱、检索、计划、工作流、附件读取、分享和历史统计，必须覆盖这些路径。
- 现有分享为快照，撤销与原始资源删除互相独立；回收站不能让已撤销分享恢复可用。项目删除与回收的交互应在 UI 和 API 统一。
- 现有卡片 `source_excerpt`、`note` 和草稿 `sources` 已有部分信息，但缺失新需求的完整状态、可编辑来源历史及可靠失效标识，不能将已有字段称作该功能完成。
- 现有数据库逻辑备份恢复验证不等同面向用户的安全迁移，也不证明附件或密钥可恢复。
